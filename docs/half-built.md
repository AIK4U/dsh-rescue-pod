# 为什么「半个急救包」比「过期的急救包」更危险

## 一句话

过期的包是**旧的但完整**，你能用它；半个包是**看着在、用的时候才失败**——而你去拿它的时候，已经没有第二次机会。

---

## 事故

一次普通的重建。构建脚本的第一步是删掉整个急救包目录，然后从源目录重新拼。删到一半，看门狗还在往包里的 `watch.log` 写日志，Windows 的文件锁让删除在**中途**失败了。

脚本报错退出。盘上留下的是：一个**删了一半的目录**，里面还有几个旧文件、几个新文件，没有清单，没有入口。

这件事真正的教训不是「删除会失败」，而是：

> **当时没有任何东西告诉人这个包是坏的。**

目录还在、名字还对、点进去还有文件。要等到真的出事、真的去用它的时候，才会发现入口脚本不在、或者清单对不上——**而那正是最坏的时刻**。

---

## 为什么「就地构建」必然有这个窗口

任何「先删旧的、再建新的」的流程，在两次操作之间都有一个瞬间：**旧的不在、新的不全**。这个窗口的宽度等于整个构建耗时——拷贝 113 MB 的话，是几十秒到几分钟。

失败可以来自任何一个环节，而且都不是假想的：

| 失败来源 | 实测 |
|---|---|
| 文件被占用 | 看门狗每 5 分钟写一次 `watch.log`；删除撞上文件锁，**删除本身半途失败** |
| 卫星文件与原产物重名 | 33 字节的卫星把包内 5347 字节的 `README.md` 静默覆盖 |
| 打包/压缩环节出错 | zip 阶段抛错时，包已经是被删过的状态 |
| 磁盘满、进程被杀 | 同上，任何时刻中断都留下残缺 |

**关键点：这些失败都不需要罕见条件。** 只要流程是「就地构建」，残缺就是一个随时可能落地的状态，而不是一种意外。

---

## 保证：先建到旁边，自检过了再换名

改法本身很短：

```
1. 所有字节写进 <pod>.staging      （活包一个字节都不碰）
2. 在 staging 上跑自检             （ASCII/BOM + 语法 + 清单）
3. 活包 -> <pod>.replaced          （一次 rename）
4. staging -> <pod>                （一次 rename）
5. 删掉 <pod>.replaced
```

换名是原子的：**「两个名字都不完整」的窗口只有一次 rename 那么宽**，而不是整个构建耗时。失败发生在第 1–2 步，活包原封不动；失败发生在第 3 步（活包被占），此时还什么都没破坏，而且报错很响。

### 三个细节是量出来的，不是猜的

**① `trap` 里必须写 `throw $_`，不能写裸 `throw`。**

PowerShell 5.1 实测（四个变体）：

| 写法 | 结果 |
|---|---|
| `trap { ...; throw }` | 原始消息**被替换成 `ScriptHalted`**——重名那条指名道姓的报错被吞掉，人只看到「ScriptHalted」 |
| `trap { ...; throw $_ }` | **消息与错误 id 都保住**，退出码仍是 1 ← 采用 |
| `trap { ...; throw $_.Exception }` | 消息保住，但错误 id 退化成 `ParentContainsErrorRecordException` |
| `trap { ...; Write-Host $_.Exception.Message; throw }` | 只把消息打在 host 上，stderr 仍是 `ScriptHalted` |

一个没人看得懂的响亮失败，不算响亮。

**② `trap` 只能认识 staging 路径。**

清理代码里只引用 `$stageDir`，**结构上无法**碰到活包。而且必须写成 `if ($stageDir -and (Test-Path ...))`：失败发生在 `$stageDir` 赋值之前时，守卫要能兜住，否则清理代码自己变成新的错误。

**③ 换名成功之后再失败（比如打包 zip），不会伤到已经换入的包。**

staging 路径在换名后**已经不存在**，所以清理代码是空转。这条保证了清理逻辑可以放心地只认 staging。

## 让保证可验证：注入失败，而不是等它发生

这条保证有个坏性质：**每次健康的构建看起来都一模一样**。没人会注意到它退化。

所以它有自己的测试，而且失败是**注入**出来的——往 `_pod-src\_extra\` 放一个与产物重名的卫星（`README.md`），命中那条「重名即响亮失败」的检查。然后断言：

```
case 1（带重名卫星）                       case 2（去掉卫星）
  构建响亮失败                             构建成功 / BUILD OK
  报错里指名碰撞的那个文件                  staging 与 .replaced 都不留
  staging 已清（不留半个包）                活包确实被换入（旧 marker 消失）
  清理动作有告诉人                          watch.log 被带过来了
  .replaced 不存在                          卫星数与源目录一致
  活包逐文件哈希未变                        清单里每条哈希都能从磁盘重算通过
  注入的文件已从源目录删掉                  zip 条目名只用 "/"，没有反斜杠
```

夹具纪律：**被测的活包是一次性的**（建在临时目录里），真包永远不是被测对象。唯一被改的真东西是 `_pod-src\_extra\`，改完在 `finally` 里删掉，并且断言它确实删掉了。

### zip 那一项是顺手挖出来的真问题

`Compress-Archive`（PS 5.1）**和** .NET Framework 的 `ZipFile::CreateFromDirectory` **都写反斜杠**当条目分隔符：实测真包 28 条里 **14 条含 `\`、0 条含 `/`**。

ZIP 规范（APPNOTE 4.4.17.1）要求 `/`。在 Linux/macOS 上 `\` 只是**普通文件名字符**，所以这种 zip 会解成一堆名字里带反斜杠的**平铺文件**，目录树没了——对一个「拷到另一台机器救命」的包，这恰好打在最要命的地方。

改用 Windows 自带的 `bsdtar`（`tar.exe`，10-1803 起随系统）：**0 条反斜杠 / 32 条正斜杠**，中文名完好，`Expand-Archive` 照样能解。测试里因此有一条断言专门盯着这件事。

## 让规矩有据可查：留戳 + 闸门

「改了构建器就必须重跑测试」是一条**手工纪律**，而手工纪律没有存量证据——它只活在人的记忆里。

实际发生过：修构建器的那一次是在**被打断的回合**里落地的，真包也重建了，但「重跑失败测试」这件事**盘上没有任何痕迹**说明它没做。当时只能靠比对清单里的时间戳和工具回执，人工判断。

机制很小：

- 测试**全绿时**写一个戳，记下构建器的 `sha256`；**失败不写戳**（空戳比没有戳更坏：它把「没测过」谎报成「测过」）。
- 一个只读比对器拿戳去比盘上的构建器。退出码：`0` 匹配 / `1` 改过或从没跑过 / `2` 读不到。
- **`2` 绝不当作 `0` 用。**「读不到」在别的脚本里经常被 `-ErrorAction SilentlyContinue` 吞掉，然后被当成「没事」。

比对器自己也要有反证用例，否则你不知道它会不会永远返回 0——本仓库的 `tests\run-tests.ps1` 里，六个分支各有一个夹具专门把它叫响。

## 一条测试自己的坑（写给写测试的人）

在 `$ErrorActionPreference = 'Stop'` 下，这样捕获子进程输出：

```powershell
$out = (& powershell ... 2>&1 | Out-String)
```

**会把子进程的第一行 stderr 变成父进程的终止性错误**：子进程真实的输出根本没进 `$out`，测试直接以「ScriptHalted」死掉。而「构建失败」按设计就是往 stderr 写——所以这个坑**只在测失败路径时才现形**，测成功路径永远遇不到。

修法：调用子进程的那一小段局部把 `$ErrorActionPreference` 降为 `Continue`（函数作用域内，不泄漏到调用方）。

**这一条本身就很说明问题**：失败路径需要被专门照顾，而它恰好是最容易被跳过的那条路径。
